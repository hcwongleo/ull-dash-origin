The content port serves both writes and reads — the same 9094 — separated only by source address in the security group. The admin port is a different listener entirely, because Files is keyed by request URL and a PUT /-/healthz would otherwise shadow the endpoint.

the journey · one 2-second segment, ~700 KB

Eight steps, and the reader starts before the writer finishes

t = 0   encoder opens the PUT~2.0 s   segment complete+12 s   DELETE
01

Elemental opens a chunked PUT

PUT /…_000000417.mp4   Transfer-Encoding: chunked
net/http accepts the connection and spawns goroutine A to run the handler.
cost: one goroutine, ~8 KB of stack
02

The file is registered before any bytes arrive

name := r.URL.String()  →  the map key, verbatim
FilesLock.Lock() → Files[name] = f → Unlock()
cost: a map insert, microseconds  ·  this is what makes read-while-write possible: readers can find the file while it is still empty
03

The body is wrapped with an idle deadline

body := withIdleDeadline(w, r)  — resets the connection read deadline before every read
cost: one syscall per chunk  ·  bounds silence, not duration, so a legitimate 2 s upload is never killed
04

Chunks arrive — ~51 KB every 0.2 s

io.Copy(f, body) → f.Write(p) for each chunk:
  lock.Lock() → buffer = append(buffer, p...) → Unlock()
  noteIngest(len(p))   cond.Broadcast() ← wakes every parked reader
cost: a memcpy plus a broadcast, per chunk  ·  ~10 chunks for this segment
05

CloudFront asks for it — while it is still arriving

GET the same path. net/http spawns goroutine B.
FilesLock.RLock() → found → !f.eof, so the response is Transfer-Encoding: chunked
NewReadCloser registers context.AfterFunc(ctx, cond.Broadcast)
cost: a map lookup and a second goroutine  ·  the player is invited to ask 1.8 s early, so this normally happens before step 04 finishes
06

Reader and writer interleave — and the reader sleeps for free

Read → copy what exists → Flush → bytes leave the box
drained but not eof → cond.Wait()  —  goroutine parks on a futex
writer Broadcasts → wakes → copies the next chunk
cost while waiting: zero  ·  upstream this same wait was a spin loop costing a full core, per viewer
07

Writer finishes, reader ends, CloudFront caches

f.Close() → eof = true → Broadcast → reader’s Read returns io.EOF → response completes
PUT returns 204. CloudFront stores the object for 6 hours.
cost: every later viewer at every POP is served from the edge — the origin sees roughly one fetch per POP, not per viewer
08

~12 s later the encoder deletes it

DELETE the same path, as the segment leaves the manifest window.
delete(Files, name) → the last reference goes → Go reclaims the buffer.
cost: a map delete  ·  27,507 of these measured in one 5-hour session — this is what bounds memory in normal operation

The important feature of that CPU trace is how much of it is empty. Work happens when a chunk arrives or a reader is woken; the rest of the time both goroutines are parked on futexes and the scheduler has nothing to run.

the same journey, upstream

One line of code changes the shape of step 06

upstream — step 06

// reader drained the buffer
return 0, nil
read → 0 bytes → retry
read → 0 bytes → retry
read → 0 bytes → retry
… millions of times per second
1.07 cores — per viewer — and it never stops, because a spinning reader never writes and so never notices the viewer left

now — step 06

for drained && !eof {
  if ctx.Err() != nil { return }
  cond.Wait()
}
copy → flush
park on futex — 0 CPU
↳ woken by the writer’s Broadcast
copy → flush
0.0036 cores total — and ctx.Err() on every wake means a departed viewer is noticed immediately

Why the wait is safe. The condition variable is built on lock.RLocker(), so every waiter is a reader holding RLock. Wait enqueues on the notify list before unlocking, and a writer cannot append while any reader holds RLock — so the Broadcast in step 04 can never be missed by a reader that has just decided to sleep.
