01 · the idea

The reader chases the writer

A normal origin hands out whole files, which puts a floor under latency: nothing can be served until a segment is complete. Here the encoder’s upload and the viewer’s download run at the same time, a fraction of a second apart.

ENCODER WRITING SEGMENT 417~700 KB over 2.0 s
VIEWER READING SEGMENT 417starts ~130 ms behind

the distance between the two heads is your latency

Measured through a real CloudFront distribution: a 426 KB segment delivered progressively over 1700 ms while still being written. A buffering origin would have sent nothing for 2 s and then dumped it.

This is exactly what S3 cannot do. S3 makes an object readable only once the PUT completes. That is why the S3 pipeline’s Lambda rewrites availabilityTimeOffset to 0 — the encoder’s “fetchable 1.8 s early” is simply untrue there. And in ap-east-1 there is no managed alternative: MediaPackage has no endpoint in the region, MediaStore is discontinued.

Why there is no CDN in front of ingest

A CDN’s value is fan-out to many readers. Ingest has exactly one writer. So an ingest CDN adds a hop and a Lambda invocation for no fan-out benefit.

The stronger argument is authorisation. With CloudFront in front of ingest, the security group must accept PUT and DELETE from CloudFront’s entire origin-facing prefix list — that is the only source address CloudFront presents. Every CloudFront distribution in the world would be inside your write perimeter.

03 · the read path — the load-bearing fix

Four bytes of code that cost a CPU core per viewer

When a reader drained everything written so far but the writer had not finished, upstream returned (0, nil). Go’s io.Copy reads that as retry immediately, with no backoff.

upstream

// reader caught the writer
return 0, nil
read → 0 bytes → retry →
read → 0 bytes → retry →
read → 0 bytes → retry →

1.07 cores — per viewer, forever

now

for drained && !eof {
  if ctx.Err() != nil { return }
  cond.Wait()
}
read → sleep on cond →
      ↳ woken by Write
read → bytes → copy

0.0036 cores — measured, live stream

A profiler put 87.67% of all server CPU inside that one function. Worse: a spinning reader never attempts a write, so it never discovers the viewer disconnected — it span forever. Four disconnected readers left an origin burning 2.43 cores permanently with two ingests wedged.

Why the condition variable is built on lock.RLocker(). Every waiter is a reader holding RLock. Wait enqueues on the notify list before unlocking, and a writer cannot append while any reader holds RLock — so a Broadcast issued after the write lock is released can never be missed. That is the entire correctness argument for the read path.

04 · locking

Two levels, so one file never blocks another

var Files    = map[string]*File{}   // keyed by request URL, verbatim
var FilesLock = new(sync.RWMutex)      // guards the MAP

type File struct {
    lock   *sync.RWMutex   // guards THIS file's bytes
    cond   *sync.Cond      // built on lock.RLocker()
    buffer []byte         // the whole object, in memory
    eof    bool           // the writer has finished
}
FilesLock — only for map lookup, insert and delete. Held for microseconds.
GET lookupPUT insertDELETEsweep
File.lock — held while streaming bytes. Many readers, one writer.
reader RLockreader RLockreader RLockwriter Lock

A reader holds only the file’s read lock while streaming, so ingest of every other segment continues untouched. This is why one slow viewer cannot stall the encoder.

A map entry is a strong reference. Go’s collector frees what is unreachable, not what is unused — so nothing here is ever reclaimed by the runtime. Verified: four test objects still resident after 18.9 hours, including across a forced GC. Everything in §06 exists because of that single fact.

05 · waking readers

Four things must wake a parked reader

A reader asleep on the condition variable is invisible to net/http. Miss any of these and it waits on a signal nobody will ever send.

bytes arriveWrite appends, then Broadcast
writer finishesClose sets eof, then Broadcast → reader returns io.EOF
viewer disconnectscontext.AfterFunc(ctx, Broadcast); Read re-checks ctx.Err() on every wake
file reclaimedDiscard sets eof, nils the buffer, Broadcast → terminal, which is correct: the bytes are gone

The two in red were real bugs. Without the first, a disconnected viewer’s goroutine spun forever. Without the second, a reader parked on a file the sweeper reclaimed waited on a condition variable no writer would signal again.

One goroutine per request

net/http runs one goroutine per request, so the count is the number of requests in flight. Measured on the deployed origin:

idle                 5
20 slow readers     25   // exactly +20
80 slow readers     85   // exactly +80
after they finish    5   // back to baseline — the healthy signal

A count that ratchets up and never falls means requests are stuck — the shape every leak in this server has had. Hence the dashboard metric and the alarm.

The bug that produced no error at all

FileReadCloser embeds *File, so rc.Close() resolved to the promoted File.Close — which sets eof. One viewer closing its connection marked the segment complete for every other viewer, silently truncating a segment still being ingested. An explicit shadowing method now fixes it. Nothing logged; it just corrupted playback.

06 · memory

Bounded three independent ways

encoder DELETEs — ~25 MB steady state

1  Elemental deletes each segment as it leaves the manifest window. 27,507 measured in one 5 h session. Does all the work in normal operation.

-idle-sweep 3600 — ~1.9 GB worst case

2  A garbage collector, not a DVR window. Covers what the encoder does not: an output that stops leaves its last window undeleted, and DELETEs stopping altogether would grow at ~1.8 GB/hour. 300× a 12 s timeShiftBufferDepth, so it cannot reach live content.

MemoryMax=25% — the cgroup ceiling

3  A kernel limit, so a runaway dies inside its own cgroup rather than letting the system OOM killer choose sshd or the SSM agent instead.

The sweeper’s three phases

1  collect under RLock          // cheap, does not block ingest
2  delete under Lock, re-checking identity
                                // a PUT between phases must not lose its replacement
3  Discard outside FilesLock   // wake parked readers, without holding the global lock

Each phase guards a bug this server has actually had. Cost measured at 5.1 µs per sweep at ~100 files, once a minute — roughly 400,000× smaller than the CPU the origin uses just serving.

Why there is no hand-maintained byte counter. An earlier build incremented on write and decremented on release, missed the decrement on one route, and drifted to 60× the true value in production — 6.1 GB reported against 81 MB actual. Worse than no metric, because it looked authoritative. Memory now comes from runtime.ReadMemStats, which cannot drift.

07 · restarts

The one file that must survive

Everything is in RAM, and Elemental Live sends initialisation segments only when an output group starts. So every restart lost them and no encoder resent them. Viewers already watching kept playing; only new viewers failed — which is why it looked healthy for hours. It caused two outages.

It also undid every automatic recovery: systemd restarts a crash in ~2 s, the watchdog catches a hang within a minute, AWS recovers a failed host unasked — and all three handed back a stream that would not accept new viewers.

// init segments only: a few hundred bytes, once per encoder run.
// media stays in RAM — a disk write per segment would buy nothing.

PUT /ch18live-v_init.mp4   →   %2Fch18live-v_init.mp4   // percent-encoded, flat

filepath.Join("/opt/gochunked/content", "/../../etc/cron.d/x")
                        → "/etc/cron.d/x"   // what we are defending against

The filename comes from an unauthenticated request URL, and this is the only code in the server that turns a request into a filesystem path. So: percent-encoded to one flat name with no separators, never exactly . or .., and the resolved path re-checked inside the directory anyway. ProtectSystem=strict would block it today — but that lives in the unit file, not the program.
